What is .NET configuration, in one sentence?	A single <b>flat dictionary of string keys</b>, assembled by stacking ordered providers, where the <b>last provider to supply a key wins</b>.<br><br>Not a file. Files are just one kind of provider.	dotnet::configuration core
Why did .NET Core replace <code>web.config</code> transforms with a provider stack?	Because build-time transforms produce a <b>different artifact per environment</b> — you test one package and ship another.<br><br>Merging providers at <i>run time</i> gives one binary/image pointed at different values.	dotnet::configuration why
What does <code>{ "Optimizer": { "Solver": { "TimeLimitSeconds": 30 } } }</code> actually become in configuration?	One entry: <code>Optimizer:Solver:TimeLimitSeconds = "30"</code><br><br>JSON nesting is <b>flattened</b> with <code>:</code> separators, and the value is a <b>string</b> — typing happens at bind time, not read time.	dotnet::configuration core
How does <code>configuration["Key"]</code> decide which provider's value to return?	It walks the provider list <b>in reverse</b> and returns the first hit.<br><br>There is no pre-computed merge. "Last registered wins" <i>is</i> the reverse iteration.	dotnet::configuration core
Give the default provider order from <code>WebApplication.CreateBuilder(args)</code>.	1. <code>appsettings.json</code><br>2. <code>appsettings.{Environment}.json</code><br>3. user secrets <i>(Development only)</i><br>4. environment variables<br>5. command-line arguments<br><br>Later overrides earlier.	dotnet::configuration core
Why can <code>ASPNETCORE_ENVIRONMENT</code> not be set inside <code>appsettings.json</code>?	Chicken-and-egg. The host builds a <b>bootstrap stack first</b> (command line + <code>DOTNET_</code>/<code>ASPNETCORE_</code> env vars) to read the environment name, <i>then</i> uses it to pick <code>appsettings.{Environment}.json</code>.<br><br>The file that would tell you which file to load is the one you are choosing.	dotnet::configuration why leech-risk
Why does the environment variable provider map <code>__</code> to <code>:</code> instead of accepting <code>:</code> directly?	Because <code>:</code> is not a legal character in an environment variable <b>name</b> on Linux — you cannot <code>export A:B=1</code>.<br><br>So <code>Optimizer__Solver__TimeLimitSeconds=120</code>. A <b>single</b> <code>_</code> is not special and silently overrides nothing.	dotnet::configuration core
Why does <code>:</code> work in a command-line argument but not in an environment variable?	The shell restriction is on variable <b>names</b>, not on argument text.<br><br><code>dotnet run --Optimizer:Solver:TimeLimitSeconds=5</code> is fine.	dotnet::configuration gotcha
A <code>--Key=value</code> command-line override is ignored. Most likely cause?	<code>args</code> was not passed to <code>WebApplication.CreateBuilder(args)</code>.<br><br>That argument <i>is</i> the command-line provider — drop it and the topmost layer silently does not exist.	dotnet::configuration gotcha
What security property does <code>dotnet user-secrets</code> actually give you?	Only one: the value is <b>outside your working tree</b>, so it cannot be committed by accident.<br><br>It is stored in <b>plaintext</b> at <code>~/.microsoft/usersecrets/&lt;UserSecretsId&gt;/secrets.json</code>. No encryption. Not for production.	dotnet::configuration gotcha
Why are user secrets registered only in the Development environment?	Because they are keyed by a GUID in your <code>.csproj</code> and read from your <b>home directory</b> — neither exists meaningfully on a server.<br><br>Production uses a different provider in the same stack: env vars, or Key Vault when you need rotation and audit.	dotnet::configuration why
You shorten a 3-item array to 2 items in <code>appsettings.Production.json</code>. What runs in production?	<b>All three items.</b><br><br>Providers merge <b>per leaf key</b>, not per section. The override wrote <code>:0</code> and <code>:1</code>; nothing wrote <code>:2</code>, so the base value survives. There is no "clear this section" — there are no sections, only keys.	dotnet::configuration gotcha leech-risk
Your options object binds to nothing but the app starts cleanly and reports healthy. What happened?	Section-name typo. The binder <b>ignores keys it cannot match and leaves unmatched properties at their defaults</b> — so you get a fully-populated object of zeros with no exception and no log line.<br><br>Fix: <code>.ValidateDataAnnotations().ValidateOnStart()</code> — crash at boot, not at 3am.	dotnet::configuration gotcha
<code>IOptions&lt;T&gt;</code> vs <code>IOptionsSnapshot&lt;T&gt;</code> vs <code>IOptionsMonitor&lt;T&gt;</code>?	<code>IOptions&lt;T&gt;</code> — singleton, computed once, <b>never</b> reloads.<br><code>IOptionsSnapshot&lt;T&gt;</code> — scoped, recomputed per request.<br><code>IOptionsMonitor&lt;T&gt;</code> — singleton, <code>CurrentValue</code> + <code>OnChange</code>.<br><br>The table is generated by one rule: a singleton resolves dependencies <b>once</b>, so a singleton that must observe changes needs the monitor.	dotnet::configuration core
Why is injecting <code>IOptionsSnapshot&lt;T&gt;</code> into a singleton a bug?	It is a <b>captive dependency</b> — the singleton resolves the scoped snapshot once and holds it for the process lifetime, so it never updates and outlives its scope.<br><br>Same bug as constructor-injecting a <code>DbContext</code> into middleware.	dotnet::configuration why
You edit <code>appsettings.json</code> in a running container and nothing changes, despite <code>reloadOnChange: true</code>. Two reasons?	1. <code>IOptions&lt;T&gt;</code> is computed once — you need <code>IOptionsSnapshot</code>/<code>IOptionsMonitor</code>.<br>2. Mounted ConfigMaps/volumes swap <b>symlinks</b> rather than writing the file, so the file watcher never fires.	dotnet::configuration deployment
<code>appsettings.Development.json</code> loads on Windows and is ignored on Linux. Why?	<b>File paths</b> on Linux are case-sensitive; the file name must match <code>ASPNETCORE_ENVIRONMENT</code> exactly.<br><br>Note the asymmetry: configuration <b>keys</b> are case-<i>insensitive</i>, file names are not.	dotnet::configuration deployment
Is <code>GetConnectionString("Db")</code> a special feature?	No. It is a plain lookup of the key <code>ConnectionStrings:Db</code>.<br><br>Which is why you can set it from an env var as <code>ConnectionStrings__Db=...</code>.	dotnet::configuration core
What does <code>global.json</code> pin, and how is the file chosen?	It pins the <b>SDK</b> (build tooling), <i>not</i> the runtime your app targets — <code>&lt;TargetFramework&gt;</code> does that.<br><br>The <code>dotnet</code> host walks <b>up</b> from the current directory and uses the nearest one. Directory proximity is the precedence rule, exactly as provider order is at run time.	dotnet::configuration core
Build works locally and fails on the CI agent with an SDK error. What is the likely <code>global.json</code> setting?	<code>rollForward</code> too strict — <code>disable</code> demands an exact version match, so a newer SDK on the agent is a hard failure.<br><br>Options: <code>latestPatch</code> (default), <code>latestFeature</code>, <code>latestMajor</code>, <code>disable</code>.	dotnet::configuration deployment
You add <code>AddJsonFile("overrides.json")</code> to <code>builder.Configuration</code> and it beats your environment variables. Why?	Because <code>builder.Configuration</code> <b>is</b> the provider list, and the default providers are already in it. Appending means registering last, and last wins.<br><br>"Configuration builders" are not a separate system — they are the list.	dotnet::configuration why
