What is a test actually worth, in one sentence?	<b>What it isolates.</b> Change one behaviour and exactly one test should fail.<br><br>Whether that is possible is a property of your <i>design</i> long before it is a property of your tests.	dotnet::testing core
Why is "this class is hard to test" a design finding rather than a testing problem?	Because it almost always means the class has a <b>dependency it never declared</b>.<br><br>The test is just the first caller that has tried to supply one. Ch. 03's seam is what testing uses.	dotnet::testing why leech-risk
A test needs six mocks to construct one class. What is it telling you?	The class has <b>six responsibilities</b>.<br><br>The response is to split the class, not to add a seventh mock.	dotnet::testing why
Why does <code>DateTime.Now</code> inside a method break testability?	It is a <b>dependency on the machine's clock that never appears in the constructor</b>.<br><br>The test cannot control it, so behaviour that changes at midnight or on a leap day can't be reproduced. Inject a clock — ch. 03's <code>IClock</code> example exists for this.	dotnet::testing gotcha
Why is asserting on private state or internal call order a bad test?	It fails on every refactor even when nothing observable changed.<br><br>That test does not protect the behaviour — <b>it prevents the refactoring</b>. Assert on what a caller could see.	dotnet::testing why
Unit vs integration — what is the real distinction?	<b>What you deliberately hold still.</b><br><br>A unit test holds everything still except one behaviour. An integration test stops holding things still so it can tell you the pieces <i>fit</i>. It is not about size.	dotnet::testing core leech-risk
Name a bug class that 100% unit coverage cannot catch.	<b>Composition bugs.</b> Every part correct, the wiring wrong.<br><br><code>UseAuthorization</code> missing so <code>[Authorize]</code> is decoration · middleware in the wrong order · a captive dependency surfacing on request two. No unit is involved in any of them.	dotnet::testing why leech-risk
What actually differs between xUnit, NUnit and MSTest?	<b>Lifecycle and parallelism</b>, not capability.<br><br>xUnit: new instance per test, collections parallel <i>by default</i>.<br>NUnit: one instance per fixture reused, <code>[SetUp]</code>, parallelism opt-in.<br>MSTest: new instance per test, opt-in.	dotnet::testing core
Why is xUnit's "new instance per test" a deliberate stance?	It makes shared state between tests <b>structurally difficult</b> rather than merely discouraged.<br><br>NUnit's reused fixture is more convenient and puts that discipline on you — a mutated field is visible to the next test, and concurrently if parallelised.	dotnet::testing why
Fake vs mock — what's the difference and which should you prefer?	<b>Fake</b> — a working implementation unsuitable for production (in-memory repo). It <i>behaves</i>.<br><b>Mock</b> — configured per test, records calls. It <i>verifies</i>.<br><br>Prefer the fake: it lets you assert on the outcome instead of on how the code works.	dotnet::testing core
Why should you "mock what you own"?	Mocking a third-party client or <code>DbContext</code> encodes <b>your assumptions about someone else's behaviour</b>.<br><br>The test then passes forever regardless of whether those assumptions are true. Wrap the boundary in your own interface and test the wrapper against the real thing.	dotnet::testing gotcha leech-risk
When is <code>Verify(..., Times.Once)</code> the right assertion?	When <b>the call genuinely is the observable behaviour</b> — an email sent, an event published, a payment taken.<br><br>Otherwise you are asserting on <i>how</i> the code works, which breaks on every refactor.	dotnet::testing why
What is the failure state of a test built from five mocks?	It is <b>a test of your mock configuration</b>.<br><br>It will stay green through a total rewrite of the logic underneath it.	dotnet::testing gotcha
What does <code>WebApplicationFactory&lt;T&gt;</code> actually start?	Your <b>real application</b> — real <code>Program.cs</code>, real DI container, real middleware pipeline, real routing — over an in-memory transport with no sockets and no port.	dotnet::testing core
How do you substitute a service in an integration test without touching <code>Program.cs</code>?	<code>RemoveAll&lt;T&gt;()</code> then re-register in <code>ConfigureServices</code>.<br><br>It works because of ch. 03's rule: <b>last registration wins</b>.	dotnet::testing core
Why should <code>Program.cs</code> stay a thin composition root?	Because <b>the more logic it contains, the less of your app an integration test actually exercises</b>.<br><br><code>WebApplicationFactory</code> runs the real one — logic hidden there is logic no test reaches.	dotnet::testing why
Why is the EF Core in-memory provider a trap?	<b>It is not a relational database</b> — it's a dictionary that speaks <code>DbSet</code>.<br><br>No referential integrity, no unique constraints, and <b>no SQL translation</b> — so a query that can't translate passes the test and throws in production.	dotnet::testing gotcha leech-risk
What are the two honest options for testing EF Core?	<b>SQLite in-memory</b> — a real relational engine, enforces constraints, catches most translation problems, but not your production dialect.<br><br><b>The real database in a container</b> (Testcontainers) — the only thing that proves a PostgreSQL query works on PostgreSQL.	dotnet::testing core
What is the "red" step in red-green-refactor actually verifying?	That the test is <b>wired to the thing it claims to test</b>.<br><br>Not ritual — evidence. Until you have watched a test fail, you have a method that passes, and passing is also what a broken test does.	dotnet::testing core leech-risk
Why does writing a test first change the design of the code?	The test is <b>a consumer of an API that does not exist yet</b> — you design the call site before the implementation, from the outside in.<br><br>Code written that way comes out with declared dependencies and observable outcomes, because otherwise the test would have been impossible to write.	dotnet::testing why
Name three cases where test-first is the wrong tool.	1. <b>You don't know the shape yet</b> — spikes, exploratory work, UI still being designed.<br>2. <b>The feedback loop isn't the bottleneck</b>.<br>3. <b>Correctness is empirical, not specified</b> — you can't assert an answer you haven't discovered.	dotnet::testing why
Correctness is empirical (tuning an optimiser). What do you do instead of TDD?	<b>Pin the result once you have it</b> — characterisation tests over known inputs, so the next tuning pass can't silently regress a case you already got right.<br><br>That's a regression harness, not TDD. Confusing the two is how people conclude TDD failed them.	dotnet::testing why leech-risk
Why write <code>LogInformation("Rack {RackId} rejected", id)</code> rather than interpolating?	The template preserves <code>RackId</code> as a <b>queryable field</b>. Interpolation collapses it to a string and the information is gone before it leaves the process.<br><br>Interpolation also formats the message even when the level is disabled.	dotnet::testing core leech-risk
What makes log levels a contract rather than a mood?	<code>Information</code> is <b>what you can afford to emit for every request in production</b>. <code>Debug</code>/<code>Trace</code> are what you turn up when something is wrong — and the level is configuration (ch. 02), so that's a settings change, not a deploy.	dotnet::testing core
When is asserting on logs legitimate?	When <b>the log is the observable behaviour</b> — an audit trail, a compliance record, a security event.<br><br>Then it's output and deserves a test like any other output. Otherwise it's testing how something works.	dotnet::testing gotcha
Ch07 covers logging, ch09 also covers logging. What is the boundary?	<b>Ch07: one process</b> — <code>ILogger&lt;T&gt;</code> as a substitutable seam, structured templates, levels.<br><b>Ch09: more than one</b> — the question becomes "what happened to <i>this request</i> across five services": correlation IDs, trace context, aggregation.	dotnet::testing core
Name four ways a suite can be green while protecting nothing.	1. <b>Assertions that cannot fail</b> (<code>Assert.NotNull</code> on a non-nullable return).<br>2. <b>Tests asserting on their own mocks.</b><br>3. <b>Tests that never run</b> — skipped, undiscovered, filtered out in CI.<br>4. <b>A build that doesn't fail on failures</b> — swallowed exit code.	dotnet::testing gotcha leech-risk
Why are flaky tests worse than no tests?	A test failing one run in twenty trains everyone that "just re-run it" is the fix — and then a <b>real</b> failure gets re-run too.<br><br>Cause is almost always shared state, real time, or ordering under parallel execution. Fix it or delete it; indefinite quarantine is deleting it with extra steps.	dotnet::testing gotcha
You wrote the code before the test. What is the cheap habit that recovers the "red" step's value?	<b>Break the code on purpose and watch it go red.</b> Comment out the line, invert the condition, return the wrong constant.<br><br>If it stays green you've learned something now rather than during an incident. Mutation testing (Stryker.NET) automates this.	dotnet::testing core
Why is high coverage a weak argument that code is tested?	Coverage measures which lines <b>executed</b>, not which behaviours are <b>protected</b>.<br><br>A suite that runs every line and asserts almost nothing scores the same as one that would catch a regression. It's a good way to find untested code, a bad way to claim code is tested.	dotnet::testing why
