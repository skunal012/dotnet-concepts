What does a service lifetime actually determine?	<b>Which container caches the instance.</b><br><br>Transient — cached nowhere, new on every resolve.<br>Scoped — cached in the scope.<br>Singleton — cached in the root provider.<br><br>"How long it lives" is the consequence; the cache is the mechanism.	dotnet::di core
What is <code>IServiceCollection</code>, mechanically?	A <b><code>List&lt;ServiceDescriptor&gt;</code></b>. Each descriptor is: service type + how to construct it + lifetime.<br><br>Resolution is a recursive graph walk over that list — find the descriptor, resolve each constructor parameter the same way, recurse to the leaves, construct back up. No magic.	dotnet::di core
You register <code>IPackStrategy</code> four times. What does <code>GetService&lt;IPackStrategy&gt;()</code> return, and how do you get all four?	The <b>last</b> registration — it is a list, and lookup takes the last matching descriptor (same rule as the configuration provider stack).<br><br>Inject <code>IEnumerable&lt;IPackStrategy&gt;</code> to get all four, in registration order.	dotnet::di core
Why do libraries register their defaults with <code>TryAddSingleton</code> rather than <code>AddSingleton</code>?	Because <b>last registration wins</b>. <code>TryAdd*</code> means "only if nothing is registered for this type yet", so the library's default does not clobber the consumer's override — regardless of which ran first.	dotnet::di why
Why is "scoped means one instance per request" a description rather than a definition?	Because the scope-per-request is a <b>convention of the ASP.NET Core hosting layer</b>, not part of the lifetime's meaning. The definition is "one per <i>scope</i>".<br><br>It matters the moment there is no request: background services, queue consumers, timers.	dotnet::di why leech-risk
A singleton constructor-injects a scoped <code>DbContext</code>. Name the <b>two</b> separate things that break.	1. <b>Shared across requests</b> — <code>DbContext</code> is not thread-safe → <code>A second operation was started on this context</code>.<br>2. <b>Used after disposal</b> — the first scope disposes it while the singleton keeps the reference → <code>ObjectDisposedException</code>.<br><br>Cause: dependencies are resolved <b>once, at construction</b>, so the singleton promotes the scoped instance to its own lifetime.	dotnet::di core
Why is "make the <code>DbContext</code> a singleton too" the wrong fix for a captive dependency?	It removes the error by moving the thread-safety problem into a class written on the assumption that it had one owner and one unit of work.<br><br>The fix is to resolve it <b>later</b>: inject <code>IServiceScopeFactory</code> and open a scope per unit of work.	dotnet::di why
The captive-dependency error appears locally but the same code runs in production. Why?	<code>ValidateScopes</code> and <code>ValidateOnBuild</code> default to <b>on only in the Development environment</b>.<br><br>So running locally with <code>ASPNETCORE_ENVIRONMENT=Production</code> — or disabling validation — turns a startup crash into silent misbehaviour. That is the argument for never turning it off.	dotnet::di gotcha leech-risk
Why can a <code>BackgroundService</code> not constructor-inject a <code>DbContext</code>?	Because <code>AddHostedService&lt;T&gt;</code> registers it as a <b>singleton</b>, started before any request exists. There is no ambient scope to inherit, so the context would be captive from the first line.<br><br>Take <code>IServiceScopeFactory</code> and <code>CreateScope()</code> per job instead.	dotnet::di core
Why does <code>services.AddSingleton(new SomeClient())</code> leave you holding a resource?	The container <b>disposes only what it created</b>. You constructed that instance, so disposal stays yours.<br><br>Use the factory overload — <code>AddSingleton&lt;IClient&gt;(sp =&gt; new SomeClient(...))</code> — if you want the container to own it.	dotnet::di gotcha
How can a <b>transient</b> service leak?	Transient is not untracked. A transient <code>IDisposable</code> is registered for disposal with <b>the scope that resolved it</b>.<br><br>Resolve one from the <b>root provider</b> (or from inside a singleton) and that scope is the application — nothing is released until process shutdown.	dotnet::di gotcha leech-risk
Memory grows steadily under a flat request rate, and nothing in your code holds state. First suspect?	<b>Transient <code>IDisposable</code> resolved from the root provider or from a singleton.</b><br><br>The instances accumulate in the root provider's disposal list for the app's entire uptime. The leak is in the container graph, not in your code.	dotnet::di deployment
Inside one request you <code>Task.WhenAll</code> over work sharing the scoped <code>DbContext</code>. What happens, and why?	<code>A second operation was started on this context before a previous operation completed</code>.<br><br>Scoped means <b>one instance per scope</b> — it says nothing about threads. Fanning out makes "scoped" mean "shared by all eight tasks you just started".<br><br>Fix: a scope per branch, or <code>IDbContextFactory&lt;T&gt;</code>.	dotnet::di gotcha
A singleton cache uses <code>ConcurrentDictionary</code>. Why is that not a performance choice?	Because the <b>registration made it shared</b>. A singleton is touched by every request simultaneously, so every mutable field in it is shared mutable state across threads.<br><br>Rule: register something as a singleton and every field it owns must be immutable or thread-safe.	dotnet::di why
Why is a second "convenience" constructor a resolution hazard?	The container picks the constructor whose parameters it can <b>all</b> satisfy — and throws when two are equally satisfiable.<br><br>So adding an overload can silently change which one runs, or break resolution entirely.	dotnet::di gotcha
<code>Unable to resolve service for type 'X'</code> appears on the first request, not at startup. Why?	Resolution is <b>lazy</b> — the graph is only walked when something is actually resolved. A missing registration is not a startup error by default.<br><br><code>ValidateOnBuild</code> (Development default) is what moves it to startup.	dotnet::di gotcha
What does a repository on top of EF Core actually buy you — and what does it not?	<b>Buys:</b> a narrower surface than <code>DbSet</code>, a seam for tests, one place for shared query logic.<br><br><b>Does not buy:</b> independence from the database — <code>IQueryable&lt;T&gt;</code> leaks provider behaviour straight through the interface.<br><br><code>DbContext</code> is already a repository (<code>DbSet&lt;T&gt;</code>) <i>and</i> a unit of work (<code>SaveChangesAsync</code>). If your methods only forward, delete the layer.	dotnet::di why
What makes "one unit of work per request" true rather than aspirational?	The <b>scoped lifetime</b> of the <code>DbContext</code>. One scope per request → one change tracker per request → one <code>SaveChangesAsync</code> that commits it.<br><br>The pattern is not implemented in your code; it is implemented by the registration line.	dotnet::di core
Why is a mediator over a single database not CQRS?	CQRS is <b>separating the write model from the read model</b> because they have different shapes — and paying for that with two models and eventual consistency between them.<br><br>A dispatcher resolving <code>IRequestHandler&lt;TCommand, TResult&gt;</code> from the container is one implementation detail of one half. MediatR is a mediator, not an architecture.	dotnet::di why
Why is <code>AddSingleton</code> strictly better than a static <code>Instance</code> property?	Because it is <b>visible in the constructor</b>. A static instance is a dependency you cannot see, cannot substitute in a test, and the host cannot dispose.<br><br>Making dependencies visible is the entire point of the container.	dotnet::di why
Which letter of SOLID <i>is</i> the container, and what do the others get from it?	<b>D</b> — dependency inversion, literally.<br><br><b>I</b>: small interfaces are cheap to register and cheap to fake. <b>O</b>: extend by registering a different implementation instead of editing a class. <b>S</b> and <b>L</b> are still yours — no container saves you from a 900-line service.	dotnet::di core
Why is injecting <code>IServiceProvider</code> into a domain service a smell?	It is the <b>service locator</b> pattern returning through the container: dependencies vanish from the constructor, scope validation cannot see them, and the class cannot be tested without a container.<br><br>Acceptable in a composition-root factory. Nowhere else.	dotnet::di gotcha
What replaced <code>HttpContext.Current</code> and the static service locator, and why was that the point?	<b>The container being part of the host.</b> The framework's own services — <code>ILogger&lt;T&gt;</code>, <code>IOptions&lt;T&gt;</code>, <code>IHttpClientFactory</code>, your <code>DbContext</code> — are entries in the same list you register into.<br><br>Ambient statics are exactly what DI replaced, which is why constructor injection "just works" in a controller you never wired up.	dotnet::di core
