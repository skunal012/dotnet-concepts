What is the one idea behind async, memory and compile-time codegen in .NET?	They are all the same principle: <b>stop paying for something during the time you are not using it</b>.<br><br>A thread held while waiting, memory held after you are done, work done at run time that was knowable at compile time.	dotnet::async-memory core
Does <code>await</code> make a request faster?	<b>No.</b> A single request is marginally <i>slower</i> — there is a state machine where there was a straight line.<br><br>What changes is <b>occupancy</b>: the same threads serve far more concurrent requests, because none is held during a wait.	dotnet::async-memory core leech-risk
Mechanically, what happens at an <code>await</code> when the operation has not completed?	The method <b>returns to its caller</b> and registers a continuation. The thread goes back to the pool.<br><br>When the I/O completes the continuation is scheduled on <i>whatever</i> pool thread is free — not necessarily the original one.	dotnet::async-memory core
When does async <i>not</i> help?	When there is <b>no external wait to release the thread during</b>.<br><br>CPU-bound work (hashing, parsing, resizing) genuinely occupies the thread. <code>Task.Run</code> just moves it to another pool thread and adds a hop.	dotnet::async-memory why
What is the fingerprint of thread pool starvation?	<b>Latency climbing steeply while CPU stays low.</b><br><br>Nothing is working hard; everything is waiting for a thread that is itself waiting. Queue high + CPU high is a different problem — saturation.	dotnet::async-memory gotcha leech-risk
Why can't the thread pool just grow its way out of starvation?	Past its minimum it injects threads at roughly <b>one or two a second</b> — hill-climbing, not allocation.<br><br>If arrivals outpace that, the queue wins. And each thread costs ~1 MB of stack to hold more waiting.	dotnet::async-memory why
Why is <code>.Result</code> worse in ASP.NET Core than in old ASP.NET?	Old ASP.NET had a <code>SynchronizationContext</code>, so it <b>deadlocked</b> — unpleasant but loud, and usually caught in development.<br><br>ASP.NET Core has none, so it <b>starves</b> instead: fine in testing, degrading under production load.	dotnet::async-memory gotcha
Why is <code>ConfigureAwait(false)</code> a no-op in ASP.NET Core?	There is <b>no <code>SynchronizationContext</code></b> to capture, so there is nothing to opt out of.<br><br>It still belongs in library code, which cannot know whether some caller has one.	dotnet::async-memory gotcha
Why is <code>async void</code> dangerous outside an event handler?	There is <b>no task to observe</b>, so an exception inside it cannot be caught by the caller — it takes the process down.<br><br>If it is not literally an event handler, it should be <code>async Task</code>.	dotnet::async-memory gotcha
What does <code>Task.WhenAll</code> over a shared scoped <code>DbContext</code> produce, and why?	<code>A second operation was started on this context before a previous operation completed</code>.<br><br><b>Scoped means one instance per scope — it says nothing about threads.</b> Parallel branches need their own context.	dotnet::async-memory gotcha
Why is "there is a memory leak" technically the wrong sentence in .NET?	Managed memory is never <i>leaked</i> — it is <b>retained</b>. The GC frees anything unreachable from a root.<br><br>So there is always a reference, and the job is finding <b>who is still holding it</b>.	dotnet::async-memory core leech-risk
Name the usual roots behind a growing .NET heap.	<b>Statics</b> (a dictionary only ever added to) · <b>event handlers</b> (publisher outlives subscriber) · <b>caches with no eviction</b> · <b>captured closures on long-lived delegates</b> · undisposed timers and subscriptions · a singleton holding something per-operation.	dotnet::async-memory core
Which counter tells you it is retention rather than churn?	<b>Gen 2 heap size across collections.</b> Climbing and never returning = retention (a root).<br><br>High <b>allocation rate</b> with a <i>flat</i> heap = churn — reduce allocations, don't hunt roots.	dotnet::async-memory why leech-risk
Why does a cache belong in a memory chapter rather than a data chapter?	Because a cache is <b>memory you have deliberately decided not to release</b>.<br><br>The storage is trivial. The only real design question is <i>when do you let go</i> — and a cache with no answer is a leak with better PR.	dotnet::async-memory why
<code>IMemoryCache</code> behind three replicas — what breaks?	It is <b>in-process</b>, so you have three caches with three different answers.<br><br>A user's next request may not see what the last one wrote. Fine for slow-moving reference data; wrong for anything a user just edited.	dotnet::async-memory deployment
Absolute vs sliding expiration — what is the trap?	<b>Sliding never expires a popular key.</b> Each access resets the clock, so a hot entry can live forever.<br><br>Occasionally what you want. Usually a surprise.	dotnet::async-memory gotcha
When is a cache with no eviction policy actually fine?	When the <b>key space is closed and you know its size</b> — bounded by the data set rather than by requests.<br><br>GROS's precomputed metric cache is this. Anything keyed by user, request or tenant is not.	dotnet::async-memory why
Why do local functions allocate less than lambdas?	A lambda that captures a variable allocates a <b>display class</b> on the heap plus a delegate.<br><br>A local function that is <i>only called directly</i> can hold its captures in a <b>struct passed by ref</b> — no allocation. Convert it to a delegate and the saving is gone.	dotnet::async-memory why
What is <code>ValueTask</code> for, and what is its one hard rule?	Hot paths that <b>usually complete synchronously</b> — a cache hit returning <code>Task.FromResult</code> allocates a task per call for nothing.<br><br>Rule: a <code>ValueTask</code> may only be awaited <b>once</b>.	dotnet::async-memory core
Why does reflection break trimming and AOT?	The linker <b>cannot see it</b>. <code>typeof(T).GetProperty(name)</code> gives no static evidence that the property is needed, so it gets trimmed away — and the failure is at run time.	dotnet::async-memory why
What do source generators actually change about the cost model?	They move the work <b>into the build</b>. A generator runs during compilation and <i>adds</i> C# to it — it never rewrites your code.<br><br>Startup reflection disappears, per-call cost disappears, the linker can see everything, and you can step into the output.	dotnet::async-memory core
Dynamic compilation is the same trade in reverse — what does it cost?	JIT cost per compilation, memory that is awkward to release, and <b>no trimming or AOT</b>.<br><br>It earns its place only when the shape genuinely is not knowable until run time: rules engines, query compilers, dynamic proxies.	dotnet::async-memory why
Nullable reference types: what is checked at run time?	<b>Nothing.</b> It is entirely compile-time. <code>string</code> and <code>string?</code> are the same type at run time; the annotations are metadata.	dotnet::async-memory core leech-risk
Why can a non-nullable <code>string</code> still be null in production?	Because the value crossed a boundary the compiler could not analyse — <b>JSON deserialisation, EF materialisation, reflection, or an unannotated library</b>.<br><br>The annotation is a claim you are making, not a guarantee the runtime enforces. Still validate at boundaries.	dotnet::async-memory gotcha
Which counter proves which problem?	<b>Threads</b> — ThreadPool Queue Length rising with low CPU.<br><b>Memory</b> — Gen 2 heap size rising across collections.<br><b>Allocation</b> — high allocation rate, flat heap.<br><b>Compile time</b> — slow cold start, fast once warm.	dotnet::async-memory core
What is the first tool to reach for on a live performance problem, and why?	<code>dotnet-counters</code> — live counters, <b>no instrumentation and no restart</b>.<br><br>It tells you <i>which</i> problem you have before you spend an hour capturing a dump for the wrong one.	dotnet::async-memory core
Why does Server GC often use more memory than you expect in a container?	It allocates a <b>heap and a background collector thread per core</b> — the right trade on a machine you own, the wrong one in a small container.<br><br>ASP.NET Core defaults to it. <code>&lt;ServerGarbageCollection&gt;false&lt;/ServerGarbageCollection&gt;</code> is often a free reduction.	dotnet::async-memory deployment
How can a container be OOM-killed while every GC counter looks healthy?	The GC only manages the <b>managed heap</b>. Thread stacks, native allocations, loaded assemblies and JIT memory live outside it.<br><br>The container limit counts all of it — so the part that grew was never the GC's to report.	dotnet::async-memory deployment leech-risk
Why does an OOM kill look like a network problem in your telemetry?	It is a <b><code>SIGKILL</code></b>. No exception, no <code>finally</code>, no shutdown hook, no log line — the process simply ceases.<br><br>The evidence is in the orchestrator (<code>OOMKilled</code>, restart count), not in the app.	dotnet::async-memory deployment
Since .NET Core 3.0, what does the runtime infer from cgroup limits?	<code>Environment.ProcessorCount</code> honours the <b>CPU limit</b>, and the GC sets a heap hard limit at roughly <b>75% of the memory limit</b>.<br><br>The trap is assuming that heap limit and the container limit are the same number.	dotnet::async-memory deployment
