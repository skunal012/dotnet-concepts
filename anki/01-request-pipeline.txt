What is the ASP.NET Core pipeline, in one sentence?	A chain of components a request travels <b>inward</b> through, and the response travels back <b>outward</b> through in reverse order.<br><br>Not a queue — a nested onion. Each component wraps everything registered after it.	dotnet::pipeline core
In middleware, what is the difference between code before and after <code>await next()</code>?	<b>Before</b> = runs on the way in (request travelling inward).<br><b>After</b> = runs on the way out (response unwinding), in <b>reverse</b> registration order.<br><br>This is just the call stack — <code>next()</code> returns only once everything deeper has finished.	dotnet::pipeline core
Mechanically, why must <code>UseExceptionHandler</code> be registered first?	Because it is a <code>try</code> block, and a try only catches what it <b>encloses</b>.<br><br>Registering it first makes it the outermost onion layer, so every later component runs inside it. Register it fifth and it cannot see exceptions from components 1–4.	dotnet::pipeline why
What happens if <code>UseAuthorization</code> is registered <b>before</b> <code>UseRouting</code>?	No error — a <b>security hole</b>.<br><br>Authorization enforces by reading <code>[Authorize]</code> metadata off the <i>selected endpoint</i>. Routing is what selects it. With no endpoint selected yet, authorization finds nothing to enforce and waves the request through. Your protected endpoint runs anonymously.	dotnet::pipeline why leech-risk
Why is routing split into two middlewares (<code>UseRouting</code> and <code>MapControllers</code>)?	So that components registered <b>between</b> them can inspect which endpoint was chosen.<br><br><code>UseRouting</code> <i>selects</i> the endpoint and attaches its metadata to <code>HttpContext</code>. <code>MapControllers</code> <i>executes</i> it. Authorization lives in the gap precisely because it needs that metadata.	dotnet::pipeline why
What does it mean for middleware to "short-circuit"?	It returns <b>without calling <code>next()</code></b>, so nothing deeper ever runs and the response unwinds immediately.<br><br>Used by: static files, HTTPS redirection, response caching, rate limiting, and authorization failures.	dotnet::pipeline core
A file in <code>wwwroot</code> is served to an unauthenticated user. Bug or by design?	<b>By design</b>, and a real gotcha.<br><br>Static file middleware short-circuits <i>before</i> routing and auth. <code>[Authorize]</code> lives on endpoints, and a static file never reaches endpoint execution. Sensitive files must not live in <code>wwwroot</code>.	dotnet::pipeline gotcha
What is Kestrel, and is it middleware?	The cross-platform <b>web server</b> — it owns the socket, parses HTTP, builds the <code>HttpContext</code>, and hands it to the pipeline.<br><br><b>Not</b> middleware. It sits in front of the pipeline and feeds it. In production it usually sits behind a reverse proxy (nginx/IIS).	dotnet::pipeline core
Difference between <code>Use</code>, <code>Run</code>, and <code>Map</code>?	<code>Use</code> — can call <code>next()</code>, passes control inward. The normal case.<br><code>Run</code> — <b>terminal</b>, never calls <code>next()</code>. Pipeline stops.<br><code>Map</code> — branches into a sub-pipeline on a path prefix.	dotnet::pipeline core
Why must authentication come before authorization?	<b>Authn = who are you</b> (builds the <code>ClaimsPrincipal</code>).<br><b>Authz = are you allowed</b> (evaluates policies against those claims).<br><br>You cannot evaluate permissions before identity has been established.	dotnet::pipeline why
Behind an nginx reverse proxy, why does the app see scheme <code>http</code> and the wrong client IP?	Because nginx terminated TLS and is the actual peer — Kestrel sees the <i>proxy's</i> connection, not the client's.<br><br>Fix: <code>UseForwardedHeaders</code>, registered <b>very early</b>, to read <code>X-Forwarded-For</code> / <code>X-Forwarded-Proto</code> before anything else inspects the context.	dotnet::pipeline deployment
You add timing middleware and it always reports ~0ms. What went wrong?	The stopwatch was stopped <b>before</b> <code>await next()</code> instead of after.<br><br>The timing only captures downstream work if you read it on the way <i>out</i> — after <code>next()</code> returns.	dotnet::pipeline gotcha
Why should you not constructor-inject a <code>DbContext</code> into a middleware class?	Middleware classes are instantiated <b>once</b> (effectively singleton), so a scoped service injected in the constructor is captured for the app's lifetime — a captive dependency.<br><br>Inject scoped services as a parameter on <code>InvokeAsync</code> instead.	dotnet::pipeline gotcha
Give the canonical middleware order and the four reasons behind it.	Exception handler → HSTS/HTTPS redirect → static files → routing → CORS → authentication → authorization → endpoints.<br><br>1. Exception handling outermost (it is a try block)<br>2. Cheap short-circuits early (don't auth a .css)<br>3. Routing before authz (authz reads endpoint metadata)<br>4. Authn before authz (identity before permission)	dotnet::pipeline core
