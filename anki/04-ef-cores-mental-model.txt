What is a <code>DbContext</code>, in one sentence?	A <b>unit of work wrapped around a change tracker</b>.<br><br>It owns the identity map, the snapshots taken at load time, and the pending change set. <code>SaveChanges</code> diffs and commits all of it in one transaction.	dotnet::ef-core core
How does EF know an entity is <code>Modified</code> when you never called an EF method?	It took a <b>snapshot</b> of the property values when the entity loaded, and compares the live object against it.<br><br>State is <i>derived</i>, not assigned. That is why a plain <code>rack.Height = 4;</code> is enough.	dotnet::ef-core core
You query the same row twice in one context. How many objects do you get?	<b>One.</b> Two round trips to the database, but the second result is matched against the identity map by primary key and the already-tracked instance wins.<br><br>This is what makes a context a unit of work rather than a cache.	dotnet::ef-core why
Why is <code>db.Update(entity)</code> usually the wrong call?	It marks <b>every</b> property <code>Modified</code>, because a detached entity has no snapshot to diff against.<br><br>Two costs: the <code>UPDATE</code> writes every column, and it silently overwrites concurrent edits — the lost-update problem the tracker exists to prevent.	dotnet::ef-core gotcha
Why does wrapping a single <code>SaveChangesAsync()</code> in <code>BeginTransaction</code> add nothing?	<code>SaveChanges</code> is <b>already a transaction</b>. It builds every command and executes all of them or none.<br><br>You need your own only for: multiple <code>SaveChanges</code> calls that must be atomic, EF mixed with raw SQL/Dapper, or a non-default isolation level.	dotnet::ef-core core
In what order does <code>SaveChanges</code> execute its statements?	By <b>foreign-key dependency</b>, computed from the model — parents before children.<br><br>The order you called <code>Add</code>/<code>Remove</code> in is irrelevant.	dotnet::ef-core why
What does a concurrency token (<code>RowVersion</code>) actually change about the generated SQL?	It adds the <b>original value to the <code>WHERE</code> clause</b>: <code>WHERE id = @id AND version = @original</code>.<br><br>Zero rows affected → someone wrote first → <code>DbUpdateConcurrencyException</code>. Without it, last write wins silently.	dotnet::ef-core why
Why can't you open a manual transaction when <code>EnableRetryOnFailure</code> is on?	A retry would replay only <b>part</b> of the transaction.<br><br>Hand the whole unit to the strategy instead, so the transaction is what gets retried:<br><code>db.Database.CreateExecutionStrategy().ExecuteAsync(...)</code>	dotnet::ef-core gotcha leech-risk
When does <code>db.Racks.Where(...)</code> hit the database?	<b>Never</b> — on its own it builds an expression tree.<br><br>Translation and execution happen when something forces enumeration: <code>ToListAsync</code>, <code>FirstAsync</code>, <code>CountAsync</code>, <code>foreach</code>.	dotnet::ef-core core
What is wrong with <code>db.Racks.ToList().Where(r =&gt; r.Height &gt; 2)</code>?	<code>ToList()</code> <b>ends translation</b>. It is <code>SELECT * FROM racks</code> — every row transferred — and the filter then runs in memory.<br><br>The type is the tell: once it stops being <code>IQueryable&lt;T&gt;</code>, you have told EF you finished composing.	dotnet::ef-core gotcha
Why did EF Core 3.0 make untranslatable <code>Where</code> clauses throw instead of evaluating client-side?	Because silent client evaluation <b>worked fine in development and melted in production</b>.<br><br>A filter that quietly moved in-memory pulls the whole table once the data grows. Failing loudly at development time is the cheaper error.	dotnet::ef-core why
What causes N+1 in EF Core, and what are the two fixes?	A navigation touched <b>inside a loop</b> — one query for the parents, then one per row.<br><br>Fix with <code>Include</code> (join it) or a <b>projection</b> (ask only for what you need). For several collection includes add <code>AsSplitQuery()</code>.	dotnet::ef-core gotcha
Why does including two collections explode the row count?	Two collection joins produce a <b>cartesian product</b> — every child of A paired with every child of B.<br><br><code>AsSplitQuery()</code> issues one query per collection instead.	dotnet::ef-core gotcha
Chapter 03 claimed a repository does not buy you database independence. What is the EF Core proof?	<b>The provider leaks through <code>IQueryable</code>.</b><br><br>On PostgreSQL <code>==</code> is case-sensitive where SQL Server's default collation is not; <code>EF.Functions.ILike</code> has no SQL Server equivalent. The C# is identical, the SQL and the results are not.	dotnet::ef-core why leech-risk
What does tracking actually cost?	A <b>snapshot per entity</b> in memory, plus change detection walking every tracked entity property-by-property on every <code>SaveChanges</code>.<br><br>Free for three entities. Not free for forty thousand loaded to compute one number.	dotnet::ef-core core
<code>AsNoTracking()</code> vs <code>AsNoTrackingWithIdentityResolution()</code> — when do you need the second?	Plain <code>AsNoTracking</code> drops the identity map too, so a duplicated row materialises as <b>separate objects</b>.<br><br>Use identity resolution when you need the graph deduplicated but still do not intend to write.	dotnet::ef-core gotcha
Why is projecting into a DTO usually a bigger win than <code>AsNoTracking</code>?	It is never tracked <b>and</b> it only fetches the columns you named.<br><br><code>AsNoTracking</code> changes the bookkeeping; a projection changes the <i>query</i>. Three columns of a fifty-column table is a different amount of I/O.	dotnet::ef-core why
What is the catch with <code>ExecuteUpdateAsync</code> / <code>ExecuteDeleteAsync</code>?	Exactly what makes them fast: they are <b>one SQL statement with no entities loaded</b>, so the change tracker never sees them.<br><br>Anything already tracked is now stale.	dotnet::ef-core gotcha
A migration is a diff. Between what and what?	Between your <b>current model</b> and <code>ModelSnapshot.cs</code> — the generated description of the model as of the last migration.<br><br><b>Not</b> against the live database. Every strange thing about migrations follows from this.	dotnet::ef-core core leech-risk
Why does hand-editing a migration file cause the <i>next</i> migration to misbehave?	The snapshot no longer matches what the migration does, so the next diff is taken <b>against a lie</b>.<br><br>Change the model and regenerate instead. Same reason two branches adding migrations conflict in the snapshot file.	dotnet::ef-core gotcha
What is <code>__EFMigrationsHistory</code> for?	It records <b>which migrations have already been applied</b>.<br><br>That is how <code>database update</code> knows where to resume, and why migrations are identified by name rather than by comparing against the live schema.	dotnet::ef-core core
Why does <code>dotnet ef migrations add</code> need your project to compile?	Because the model only exists as the result of running <code>OnModelCreating</code> on a <b>real <code>DbContext</code> instance</b>.<br><br>The tooling builds your project and constructs the context at design time. A build error is a tooling error wearing a disguise.	dotnet::ef-core why
Why does <code>dotnet ef</code> have both <code>--project</code> and <code>--startup-project</code>?	Because the <code>DbContext</code> and the host that configures it often live in <b>different assemblies</b>.<br><br>It needs one to find the model and the other to find the connection string and host builder.	dotnet::ef-core core
When does <code>IDesignTimeDbContextFactory&lt;T&gt;</code> become necessary?	When the tooling cannot construct your context from the host builder — a <b>class library</b>, or a <code>Program.cs</code> that does real work on startup.	dotnet::ef-core core
EF Core or Dapper — what is the question really asking?	<b>Does this code path want a change tracker?</b><br><br>Keep EF where there is a write model with invariants and a unit of work. Reach for Dapper where the SQL is the point: reporting, window functions, CTEs, hot read paths.	dotnet::ef-core why
What is the honest qualification to "Dapper is faster than EF"?	Most of the read-side gap closes with <b><code>AsNoTracking</code> and projections</b>.<br><br>And Dapper does not produce a better <i>plan</i> — it produces the plan for the SQL you wrote, which may be worse than EF's.	dotnet::ef-core why
Name three things that break when <code>Migrate()</code> on startup meets three replicas.	1. <b>They race</b> — all three boot and try to apply the same migration.<br>2. <b>No rollback</b> — a half-applied migration crash-loops the app that would diagnose it.<br>3. <b>Permanent DDL rights</b> for the runtime account.<br><br>Plus: the new schema lands while old instances still serve traffic.	dotnet::ef-core deployment leech-risk
Why is auto-migration on startup an ordering problem even when it succeeds?	The new schema arrives when the <b>first new instance boots</b>, while old instances are still running against it.<br><br>Any destructive change breaks them mid-rollout. That is what expand/contract is for — add, dual-write, backfill, drop in a later release.	dotnet::ef-core deployment
What should you deploy instead of calling <code>Migrate()</code>?	<code>dotnet ef migrations script --idempotent</code> as a <b>build artifact</b>, applied as an explicit step — init container, release stage, or job that completes before the new version starts.<br><br>Reviewable in a PR, identical in staging and production, and it fails before anything serves traffic.	dotnet::ef-core deployment
Why can a database created with <code>EnsureCreated()</code> never accept a migration?	It creates the schema straight from the model and writes <b>no <code>__EFMigrationsHistory</code> rows</b>.<br><br>Migrations have no idea what state it is in. It belongs in throwaway test fixtures and nowhere else.	dotnet::ef-core gotcha
