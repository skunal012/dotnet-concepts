What is the one idea that makes Docker, Kubernetes, App Service and Lambda variations rather than four topics?	<code>dotnet publish</code> produces a <b>self-sufficient folder</b>.<br><br>Every one of them is a different answer to <i>where does that folder run</i> and <i>who makes more copies of it</i>.	dotnet::build-ship core
What does <code>publish</code> add over <code>build</code>?	It gathers <b>everything needed to run</b> into one directory — assemblies, NuGet dependencies copied out of the cache, <code>appsettings.json</code>, <code>wwwroot</code>, plus <code>.deps.json</code> and <code>.runtimeconfig.json</code> telling the host what to load.	dotnet::build-ship core
Framework-dependent vs self-contained — which is the better default and why?	<b>Framework-dependent</b>, when you control the base image or host.<br><br>A runtime security patch then arrives by <b>rebasing</b> rather than by rebuilding your application. Self-contained earns its place when you can't rely on what's installed.	dotnet::build-ship why
What is deliberately NOT in the published folder?	<b>The configuration for the environment it will run in.</b><br><br>Connection strings and secrets arrive at run time from the provider stack (ch. 02). That's the property that makes one artifact deployable everywhere.	dotnet::build-ship core leech-risk
Why does copying the <code>.csproj</code> and running <code>restore</code> before copying source change build times?	The <b>restore layer is cached</b> and reused on every build where dependencies didn't change — which is almost all of them.<br><br>Copy everything first and you re-download the world on every commit.	dotnet::build-ship why
Why must the final Docker stage use the runtime image, not the SDK image?	The SDK image is roughly <b>ten times the size</b> and contains a compiler, a package manager and <b>your source code</b>.<br><br>Shipping it is both waste and a larger attack surface.	dotnet::build-ship gotcha
Why did the default ASP.NET Core container port move from 80 to 8080 in .NET 8?	So the process could run as a <b>non-root user</b> — ports below 1024 are privileged.<br><br>The images define <code>$APP_UID</code> for the same reason. A container running as root is one escape bug from a host compromise.	dotnet::build-ship deployment
What property of container images makes them worth the ceremony?	<b>Immutability.</b> The image that passed your tests is bit-for-bit the image in production, referenced by digest.<br><br>That's ch. 02's "one artifact, many environments" delivered by the packaging rather than promised by discipline.	dotnet::build-ship why
Why is <code>__</code> the config nesting separator rather than <code>:</code>?	Because environment variables are how a container is configured, and <b>a colon can't be expressed</b> in a Dockerfile, Compose file, Kubernetes manifest or App Service setting.	dotnet::build-ship core
Rank the ways of supplying a secret, best last.	1. <b>Env vars</b> — visible to anything reading the process environment, and to <code>docker inspect</code>.<br>2. <b>Orchestrator secret store</b> — mounted at run time, not baked in.<br>3. <b>A vault</b> — as a configuration provider.<br>4. <b>No secret at all</b> — managed identity. Nothing to leak.	dotnet::build-ship deployment
How does "integrate Azure services" reduce to things you already know?	A connection detail from <b>configuration</b> (ch. 02) + a client registered in <b>DI</b> (ch. 03) + credentials that ideally aren't credentials (managed identity).<br><br><code>DefaultAzureCredential</code> resolves to your dev login locally and the managed identity in production — same code, different inputs.	dotnet::build-ship core
Vertical vs horizontal scaling — what is the real difference?	<b>Vertical</b> = a bigger machine. Bounded, and does nothing for availability — one machine is still one thing that can die.<br><br><b>Horizontal</b> = more copies of the folder. Effectively unbounded, redundancy for free, and it has exactly one requirement: <b>the copies must not need to know about each other</b>.	dotnet::build-ship core
Name five things that break the first time replicas go from one to three.	1. <code>IMemoryCache</code> inconsistent per process.<br>2. In-memory sessions vanish.<br>3. A scheduled job runs three times.<br>4. SignalR messages reach some clients (needs a backplane).<br>5. <b>Users logged out at random</b> — data protection keys.	dotnet::build-ship deployment leech-risk
What is wrong with sticky sessions as an answer to horizontal scaling?	Pinning a user to one replica <b>doesn't make the app stateless — it hides that it isn't</b>.<br><br>You lose even load distribution, you lose clean node draining, and every affected user's session dies with the instance.	dotnet::build-ship why leech-risk
Why is autoscaling always reacting late?	Scaling out takes time — <b>pulling an image, starting a process, warming a JIT</b> (ch. 05 §6).<br><br>A rule tuned to a slow-moving metric responds to load that has already arrived.	dotnet::build-ship deployment
What is the axis that every hosting option (VM → PaaS → containers → Kubernetes → serverless) trades on?	<b>How much of the floor you want to own.</b><br><br>Reading down you give up control and get back operational burden. Practical guidance: take the <b>highest</b> row that meets your requirements.	dotnet::build-ship core
What is the single idea that makes Kubernetes make sense?	<b>You declare desired state; a controller continuously reconciles actual state to match.</b><br><br>You don't tell it to start three pods — you tell it three pods should exist, forever. Kill one and it reappears because the loop noticed a mismatch.	dotnet::build-ship core leech-risk
Liveness vs readiness vs startup probes — what does failing each one do?	<b>Liveness</b> — restart the container.<br><b>Readiness</b> — remove it from the load balancer, no restart.<br><b>Startup</b> — suppresses the other two until boot finishes.	dotnet::build-ship core
Describe the outage caused by checking the database in a liveness probe.	A 30-second database blip fails liveness on <b>every replica simultaneously</b>, so Kubernetes restarts the entire fleet.<br><br>A recoverable hiccup becomes a full outage, plus a thundering herd of reconnecting pods against a database already struggling.	dotnet::build-ship gotcha leech-risk
Why is a rolling update a database problem as much as a deployment one?	Because <b>old and new code are both live against one database</b> during the rollout.<br><br>A destructive schema change breaks the version still serving traffic — ch. 04 §8's expand/contract argument.	dotnet::build-ship deployment
What does serverless discard, and what follows from it?	It keeps the code and discards <b>the process</b>.<br><br>So: cold starts are the defining cost, expensive setup must live outside the handler, there's no ambient state between invocations, and execution time is capped.	dotnet::build-ship core
Why must a serverless function initialise its <code>HttpClient</code> or DI container outside the handler?	Anything constructed outside is <b>reused while the instance stays warm</b>; anything inside pays the cost on every invocation.<br><br>It's ch. 03's lifetime question with the process boundary removed.	dotnet::build-ship why
Where does serverless fit badly?	Where <b>cold starts are user-visible on a latency-sensitive path</b>, or where work is long-running and stateful.<br><br>It fits well for event-driven, spiky or infrequent work, where scale-to-zero means paying nothing to be available.	dotnet::build-ship why
What is the rule that makes a CI/CD pipeline worth having?	<b>Build once, deploy many.</b> Produce one artifact and promote <i>that</i> artifact through environments.<br><br>Build production separately from staging and you tested one thing and shipped another — ch. 02's <code>web.config</code> transform argument, with more YAML.	dotnet::build-ship core leech-risk
Why is a pipeline with <code>continueOnError</code> on its test job worse than no pipeline?	It reports failures and <b>enforces nothing</b> — so it manufactures confidence.<br><br>Ch. 07 §9: a suite nothing enforces is decoration.	dotnet::build-ship gotcha
Why tag images with the commit SHA rather than <code>latest</code>?	Because <code>latest</code> is <b>a name that doesn't identify anything</b>.<br><br>You cannot say which bytes are in production, cannot roll back to a known point, and cannot prove the deployed image is the tested one.	dotnet::build-ship deployment
Rolling vs blue-green vs canary — what does each cost?	<b>Rolling</b> — gradual, both versions live (schema constraint).<br><b>Blue-green</b> — parallel environment, fast rollback, <i>double the infrastructure</i>.<br><b>Canary</b> — a fraction of traffic first.<br><br>All three assume your database change is backward-compatible.	dotnet::build-ship core
What is the data protection key ring, and what is its default location?	The key used to encrypt everything ASP.NET Core protects for itself — <b>auth cookies, antiforgery tokens, TempData, <code>IDataProtector</code></b>.<br><br>By default generated on first use and written to the <b>local filesystem</b>.	dotnet::build-ship core leech-risk
"Users get logged out at random since we scaled out." Why, and why do the logs not say so?	<b>Each replica generated its own data protection key ring</b>, so a cookie issued by A cannot be decrypted by B.<br><br>Nothing in the logs mentions <i>key</i>, and the natural suspects — session, load balancer, cookie expiry — are all wrong.	dotnet::build-ship deployment leech-risk
Why does <code>SetApplicationName</code> matter for data protection?	The <b>application name is part of the key derivation</b>.<br><br>Two replicas of the same app match automatically. Two <i>different</i> apps that must share cookies — an MVC front end and an API on one domain — will not, unless you say so.	dotnet::build-ship gotcha
